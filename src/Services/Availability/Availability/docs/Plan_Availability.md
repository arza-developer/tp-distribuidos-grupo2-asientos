## Context

### Fase 2 – Solicitud de reserva (comando) y mensajería

**Objetivo:** `POST /api/reservations` valida que el asiento exista, registra la solicitud localmente (`Pending`), publica `ReservationRequestedEvent` en la cola `booking-requests-queue` (Azure Queue) y responde **202** sin esperar a Booking (paso 3 del TP; frontera de consistencia eventual 3.g). Si el broker falla, no hay 202.

**Contrato a preservar** (de `Availability.Api`, solo lectura): body `{eventId, seatNumber, userId, price}`; 202 con `{reservationId, status:"Pending", message:"Solicitud recibida y encolada para procesamiento", checkStatusUrl:"/api/reservations/{id}"}`; evento = `SeatsReservation.Contracts.Events.ReservationRequestedEvent` y puerto `IMessagePublisher.PublishAsync<T>(msg, queue, ct)` (se reutilizan, no se duplican).

**Decisiones propuestas (ajustables):**
1. **`SeatRequest : EntityBase`** con `int Id` interno y `Guid ReservationId` como referencia externa (índice único). Referencia al asiento por el Guid `SeatId` (no por FK int), más `EventId`, `SeatNumber`, `UserId`, `Price`, `Status` (`ReservationStatus`), `RequestedAtUtc`, `CorrelationId`. Repositorio por tipo: `ISeatRequestRepository : IGenericRepository<SeatRequest>` + `SeatRequestRepository` (interfaz vacía por ahora; `FindByReservationIdAsync` se agrega en Fase 3).
2. **Asiento inexistente → 404** (ProblemDetails). **No se rechaza por `Seat.IsAvailable`**: el flag local puede estar desactualizado y la exclusión mutua la decide Booking (índice único, TASK_02).
   > **Actualización 2026-11-01 (usuario):** esta decisión fue reemplazada: el handler ahora rechaza asientos no disponibles (`SeatUnavailableException`, code `seat.unavailable`) y marca `Seat.IsAvailable=false` al reservar.
3. **Precio:** se publica el precio del catálogo (fuente de verdad); el `price` del body se acepta por compatibilidad pero no se usa (si difiere se loguea warning).
4. **Orden y compensación:** guardar `Pending` → publicar → si falla la publicación, eliminar el registro y devolver **503** (no queda Pending huérfano). Sin outbox (sobreingeniería para el TP); queda anotado como mejora.
5. **Errores de negocio vs. técnicos (T2.0, evaluado contra la arquitectura):** `BusinessException` abstracta en Domain (solo BCL, no agrega comportamiento a las entidades anémicas) con categorías abstractas `BusinessNotFoundException` (→404) y `BusinessValidationException` (→400) y concretas `SeatNotFoundException` / `InvalidReservationRequestException`. Cumple Clean Architecture con una salvedad: los fallos **técnicos** (broker caído) NO son de negocio, por eso `MessagePublishException` vive en Application y no hereda de `BusinessException` (→503). El mapeo a HTTP se hace en Web por categoría con un `IExceptionHandler` (ProblemDetails + `code`), nunca con códigos HTTP en Domain. Sin patrón Result (más ceremonia).
6. **CorrelationId:** puerto `ICorrelationIdAccessor` en Application; en esta fase Web lo implementa con `HttpContext.TraceIdentifier` (como el stub actual); T4.2 lo reemplaza por el header `X-Correlation-ID`.
7. **Auth:** el endpoint queda **sin `[Authorize]` hasta T4.1** (igual que el stub actual); se anota para no olvidarlo.
8. **Logging INICIO/FIN** no se implementa aquí (T4.3, `LoggingBehavior`); el handler solo loguea warning/error de fallos.
9. **Azure Queue:** `Azure.Storage.Queues` 12.x, mensaje JSON (`JsonSerializerDefaults.Web`, camelCase) con `MessageEncoding = Base64` (compatible con consumidores estándar), cola creada si no existe (una vez por nombre), `AzureQueue:ConnectionString` (default `UseDevelopmentStorage=true`, Azurite), reintentos y timeout cortos (`MaxRetries=1`, `NetworkTimeout≈5s`) para fallar rápido con 503. Los errores del SDK se envuelven en `MessagePublishException` (Application no conoce tipos de Azure).

### Fase 3 – Seguimiento de estado (`GET /api/reservations/{id}`)

**Objetivo:** paso 7 de la consigna: el usuario consulta el resultado **a través de Availability**, que consulta a Booking por REST (`GET /api/bookings/{id}`). Contrato actual de Booking (stub, solo lectura, `src/Services/Booking.Api/Controllers/BookingsController.cs`): `{ReservationId, SeatNumber, Status:"Retenida"|"Confirmada"|"Rechazada"|"Vencida", ExpiresAtUtc}`, puerto 5102, sin autenticación todavía.

**Decisiones (ajustables):**
1. La query busca **primero la solicitud local** (`ISeatRequestRepository` por `ReservationId`); inexistente → **404** `reservation.not_found` (`ReservationNotFoundException : BusinessNotFoundException`). Availability no reenvía ids arbitrarios a Booking.
2. **La query es pura (CQRS):** no escribe nada (ni `SeatRequest.Status` ni `Seat.IsAvailable`). Devolver `IsAvailable` a `true` sigue en **TD-1**; esta fase deja el mapeo de estados que TD-1 reutilizará.
3. Resultados: Booking 200 → estado mapeado + `expiresAtUtc`; Booking 404 (aún no procesó el mensaje) → **200 `Pending`** con mensaje (consistencia eventual, 3.g); Booking caído/timeout/5xx/estado desconocido → **503** (`BookingUnavailableException`, técnica, no hereda de `BusinessException`).
4. **Mapeo de estados en un solo punto** (anti-corruption layer, `BookingClient`): `Retenida→Retained`, `Confirmada→Confirmed`, `Rechazada→Rejected`, `Vencida→Expired`; valor desconocido = fallo técnico.
5. Respuesta aditiva respecto del stub viejo: `{reservationId, status, message, seatNumber, expiresAtUtc}`. Sin motivo de rechazo (el stub de Booking no lo define; a acordar).
6. `HttpClient` tipado, `Booking:BaseUrl` (default `http://localhost:5102`), `Booking:TimeoutSeconds` (5), header `X-Correlation-ID`. Sin token (lo agrega T4.4) y sin Polly en esta fase.
7. `Location` en el 202 del POST cuando exista la ruta (T3.4).
8. El antiguo T3.4 ("isAvailable consciente de reservas") se descarta: lo reemplazan el guarda `IsAvailable` y TD-1.

## Deuda técnica
- **TD-1 – Flujo que devuelve `Seat.IsAvailable` a `true` — RESUELTA PARCIALMENTE (sincronización al consultar).** El flag local es un **guarda de idempotencia y concurrencia** ante la consistencia eventual con Booking: al aceptar una reserva se marca `false` y cualquier nuevo pedido para ese asiento se rechaza (`SeatUnavailableException`, 409) sin llegar al broker. Para **limitar los asientos bloqueados sin motivo**, el flag se restaura en tres casos:
  1. **Falla la publicación** al broker: compensación en `RequestReservationCommandHandler` (elimina la solicitud y libera el asiento).
  2. **Se consulta la reserva** (`GET /api/reservations/{id}` → `SyncReservationStatusCommandHandler`): el estado informado por Booking manda. `Rejected`/`Expired` → se guarda el estado y se libera el asiento (salvo que otra solicitud local activa —Pending/Retained/Confirmed— lo retenga); `Retained`/`Confirmed` → se guarda el estado y el asiento queda bloqueado (también revierte una expiración por huérfana si Booking la procesó tarde).
  3. **Huérfana** (caída entre guardar y publicar, o mensaje que Booking nunca toma): si Booking responde que **no la conoce** y la solicitud sigue `Pending` pasado `ReservationSync:PendingTimeoutMinutes` (10), se marca `Expired` y se libera. **Con Booking caído no se escribe nada** (caído nunca expira ni libera).

  **Límite conocido:** solo reconcilia lo que alguien consulta; una reserva que nadie consulta sigue bloqueando el asiento. Además cada consulta cuesta 1 llamada a Booking por reserva.

  **Alternativas a futuro (no implementadas):**
  - **Worker de reconciliación** (`BackgroundService`) que recorre las solicitudes `Pending`/`Retained` y sincroniza sin depender de que alguien consulte. Para que el trabajo **no escale por acumulación** (1 request por reserva y por ciclo), requiere un **nuevo GET en Booking que devuelva una lista** (batch), p. ej. `GET /api/bookings?reservationIds=a,b,c` (o `POST /api/bookings/query`) con estado y vencimiento de cada id (los ids desconocidos simplemente no vienen en la lista).
